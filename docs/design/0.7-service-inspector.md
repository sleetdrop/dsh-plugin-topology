# 0.7.0 — Service inspector + startup timeline

Status: **released in 0.7.0** (tag `v0.7.0`, 2026-10-19). Supersedes the 0.7.0 row in
[`navigation-ux.md`](navigation-ux.md) (B focus / state colors / minimap move
to 0.7.x). Quality plan: [`../QUALITY.md`](../QUALITY.md).

## 0. Boundary: loaded-only

This plugin is itself a plugin. If DSH fails **before or while** loading it,
the host service, panel and `diagnose` code do not exist. 0.7.0 therefore
targets **L2 only**: the DSH web UI is up and this plugin is loaded.

| Situation | 0.7.0 |
| --- | --- |
| **L0** DSH cannot start | Out of scope. Belongs to the DSH assembler/loader, an official `dsh doctor`, or pre-boot tools such as `dsh-plugin-ops` / `dsh-composition-doctor` / `dsh-doctor`. |
| **L1** Cordis starts, web UI fails | Out of scope for the panel. A headless CLI could exist later; not 0.7.0. |
| **L2** DSH web UI + plugin loaded | In scope: service inspector, missing services, live findings, panel. |

We do **not** build a boot rescue, a pre-boot static checker, or a generic
`dsh doctor`. When the panel cannot load, we are not the tool that saves the
session; the community/official pre-boot tools are, and the README should say so
plainly.

## 1. Why this slice

0.6 made service search dim the graph to a service's edges, but the right rail
stayed empty — the user got a highlighted picture without a readable answer.
The unresolved badge on a node is a count, not the missing service names.
Plugin authors ask two concrete questions:

- **“This service — who provides it, who uses it, and is it a single point of
  failure?”**
- **“My plugin declares an inject and nothing provides it — what exactly is
  missing?”**

This slice answers both with data already in `TopologyAnalysis`, plus two cheap
graph additions: **service bus factor** and **direct dependent count**.
Transitive impact, articulation/dominator criticality, DAG layers, transitive
reduction, cycles and diffs stay in 0.7.x.

## 2. 0.7.0 scope

1. **Service inspector** in the right rail, entered from the existing service
   search.
   - Header: service name, scope (when not `root`), provider count, consumer
     count, bus factor, critical/single-provider status.
   - `Providers · N` and `Consumers · M` sections, independently scrolling,
     reusing the rail shell/rows.
   - Click a row → select + fly to that plugin; the service mode clears.
2. **Missing services** in the node inspector: the actual unresolved services
   for the selected plugin (name, declared state, no-provider hint), not just a
   count.
3. **Minimal live findings**: `missing-provider`, `single-provider-service`,
   `critical-service`, `provider-not-active`. The four facts are surfaced
   inline (missing-services block, severity badge, provider state rows); the
   pure `diagnose` returns the same four for the 0.7.x model/CI exports.
4. **Two cheap graph data points**: service **bus factor** (provider count) and
   plugin **direct dependents** (`nodeMetrics.inDegree`), plus the
   **service-mediated edge weight** already derivable from `neighbor.services`.
5. **Startup timeline**: one continuous creation-ordinal heat strip in the rail.
   A neutral density gradient is the background; the selected node's instances
   are charcoal hairlines (one per ordinal; no filled span when merged); direct
   dependencies are indigo hairlines, dependents ochre, and a dependency created
   after the selected instance is a coral **late provider** hairline. The key
   sits above the strip;
   hover shows ordinal/plugin/state, click selects and flies. Service mode uses
   the same strip with provider/consumer hairlines.
6. Tests for the pure service/missing/diagnose/timeline models and a UI smoke of
   the service search → inspector → node flow and the timeline marks.

Out of 0.7.0: model tool, CI export, headless/L0, transitive impact, SPOF
criticality, DAG layers, reduction/cycles, diff, the 0.6 design's B focus/state
colors/minimap.

## 3. Data model

### Existing data (no host change)

- `analysis.graph` — the raw bipartite graph. `ServiceNode` id is
  `s:<scope>:<name>`; `provides` edges run plugin → service; `injects` edges run
  service → plugin; `graph.unresolved` has plugin id + service name + state.
- `analysis.collapsed` — plugin-to-plugin `DependencyEdge` with the mediating
  `service`; one edge per (consumer, provider, service). The collapsed
  `providers` map keeps **one provider per service**, so the raw graph is
  required for provider counts / duplicate providers.
- `analysis.nodeMetrics[id].inDegree` — direct dependents; `Dependents · N` is
  already visible.
- The selected node's `neighbor.services` — the service set behind a dependency
  edge; this is the edge weight.

### New pure module: `src/service-model.ts`

No DOM, no DSH; imported by the panel and testable in `node:test`.

```ts
export interface ServiceInspection {
  readonly id: string                 // ServiceNode.id, s:<scope>:<name>
  readonly service: ServiceNode
  readonly providers: readonly PluginNode[]   // raw provides sources
  readonly consumers: readonly PluginNode[]   // raw injects targets
  readonly providerCount: number
  readonly consumerCount: number
  readonly busFactor: number          // providerCount
  readonly severity: 'critical' | 'single-provider' | 'healthy'
  readonly edges: readonly DependencyEdge[]   // collapsed edges using this service
}

export interface MissingService {
  readonly plugin: PluginNode
  readonly service: string
  readonly state: PluginState
}

export type FindingKind =
  | 'missing-provider'
  | 'single-provider-service'
  | 'critical-service'
  | 'provider-not-active'

export interface Finding {
  readonly kind: FindingKind
  readonly severity: 'error' | 'warn' | 'info'
  readonly subject:
    | { readonly kind: 'plugin'; readonly id: string; readonly label: string }
    | { readonly kind: 'service'; readonly id: string; readonly label: string }
  readonly message: string
  readonly evidence: readonly string[]
  readonly suggestion: string
}
```

Rules:

- `providers` / `consumers` come from the **raw** graph, deduped by plugin id,
  sorted by state severity then label.
- `busFactor === providerCount`.
- `severity`:
  - `critical`: exactly 1 provider and `consumerCount >= 5` (threshold open;
    see §10).
  - `single-provider`: exactly 1 provider and `consumerCount < 5`.
  - `healthy`: 2+ providers (or 0 consumers with 2+ providers).
- `provider-not-active`: at least one provider is `FAILED` or `PENDING`;
    `critical` when the service has consumers.
- `missing-provider`: one per `graph.unresolved` row for the selected plugin
    (merged nodes aggregate their member ids); severity `error` when the
    declaring plugin is `ACTIVE`, otherwise `warn`.

The pure functions are `inspectService(analysis, id)`, `missingServices(analysis,
pluginIds)`, and `diagnose(analysis): Finding[]`.

### New pure module: `src/startup-timeline.ts`

```ts
export interface TimelineInstance {
  readonly ordinal: number
  readonly plugin: PluginNode
  readonly state: PluginState
  readonly role: 'selected' | 'instance' | 'dependency' | 'dependent'
  readonly lateProvider: boolean
}

export interface StartupTimeline {
  readonly min: number
  readonly max: number
  readonly total: number
  readonly global: readonly TimelineInstance[]      // one per drawn plugin instance
  readonly selected: readonly TimelineInstance[]    // merged instances of the subject
  readonly dependencies: readonly TimelineInstance[]
  readonly dependents: readonly TimelineInstance[]
  readonly lateProviders: readonly TimelineInstance[]
  readonly service?: {
    readonly providers: readonly TimelineInstance[]
    readonly consumers: readonly TimelineInstance[]
  }
}
```

- Ordinals come from `PluginNode.id` (`p:<n>`) and the rendered label
  (`[48,93]`); the merged display node carries every member ordinal.
- The global row covers `min..max` — the actual creation range, not a resized
  index. `total` is the number of instances.
- `lateProvider` is true for a dependency whose ordinal is greater than the
  **smallest** selected ordinal: the provider was created after the consumer.
  This is a timeline hint in 0.7.0; a formal finding is 0.7.x.
  > 0.8 removed the separate late/deferred mark entirely: the timeline shows
  > only selected / dependency / dependent and lets the x-axis carry creation
  > order; see `0.8-ui-page.md`.
- Service mode uses the raw graph providers/consumers; the roles are
  `instance` (provider/consumer), with the service group separating them.

## 4. UI

### Rail hierarchy

```
identity (name / state / source / actions)
filter
missing services (warning, when present)
startup timeline (heat strip + role hairlines)
direction sections (the primary lists)
footer hint
```

The timeline is deliberately a 32–40px context strip, not a hero: the sections
stay the primary surface. Service mode:

```
#service + scope
counts / bus factor / critical
startup timeline (providers ●, consumers ●)
Providers · N / Consumers · M
```

### Startup timeline

One continuous 1D heat strip, no segmented bars and no symbols:

- **Background**: all instances across `min..max`, rendered as a neutral density
  gradient (32 bin centers interpolated, so there are no block boundaries).
  There is no separate "all" row; the instance count lives in the band tooltip
  rather than the header, so the small strip does not spend space repeating it.
- **Selected**: a charcoal 3px hairline at each instance ordinal (near-black
  in light, near-white in dark — the conventional playhead/current-position
  neutral). Merged instances show one hairline per ordinal; the key lists
  `selected #48, #93`. There is deliberately no filled span between them: the
  earlier span read as a darker "mask" over the heat, i.e. like a bug.
- **Direction**: one cue, not a new row: the header reads `#min → #max`
  (left-to-right). It is enough to say "earlier → later" without adding an axis
  line, end labels or an animation; it also makes a red late-provider hairline
  to the right of the selected hairline immediately legible as "later".
- **Palette**: role colors are muted by mixing the theme state tokens with
  `label-secondary` — indigo/slate for dependencies, ochre for dependents,
  coral for late providers, charcoal for selected. This avoids the saturated
  web-safe primaries and still adapts to dark theme; the heat uses a neutral
  tertiary gray, and the band is a bordered `bg-layer-1` surface rather than
  the row-hover fill.
- **Relationships**: direct dependencies are blue 2px hairlines, dependents are
  amber hairlines. Color plus the key above the strip distinguishes them; the
  hairlines are annotations on the heat, not data grid lines.
- **Exception**: a dependency created after the selected instance is a red
  hairline with a `late provider` key entry. Red is reserved for this.
- **Key above the strip**: `selected #48, #93 · dependency · dependent ·
  late provider`. It is deliberately above the band (with a gap) so it cannot
  be mistaken for part of the data; the earlier below-band legend read as data.
- Hover: native title `#48 · SessionStore · ACTIVE · dependency`; click on a
  dependency/dependent hairline selects and flies. The 9px hit area is
  transparent, so it looks like a hairline, not a button; keyboard focus shows
  a thin outline.
- Service mode: the same neutral heat strip with blue provider and amber
  consumer hairlines; no selected hairline because a service has no ordinal.
- Both themes use the existing label/direction/error tokens through the
  `--dsh-tl-*` role variables; the density is neutral and the only text is the
  9px key. The band is a bordered surface (`bg-layer-1` + `border-l2`), not
  the row-hover fill, so it cannot be confused with a hovered neighbour row.
  In dark theme the selected hairline inverts to near-white and keeps a
  contrasting ring. The strip stays in the rail for 0.7.0 because it is node
  context; 0.7.x can add a wider canvas-bottom variant and brush/zoom.
### Rail modes

The rail becomes a mode switch: **node / service / empty** (the existing
collapsed strip stays).

- Node mode: unchanged 0.6 behavior, plus a **Missing services** block.
- Service mode: the new service inspector; the graph keeps the existing
  service-edge dimming.
- Empty mode: the current “Select a plugin” / service-highlight hint.

### Service inspector

- Header: `#service`, a `scope` badge when not `root`, `N providers · M
  consumers`, a `bus factor` value, and a `critical` / `single-provider` badge.
  `bus factor 1` is the headline number; the badge explains the consequence.
- Sections, reusing the independently scrolling rail sections:
  - `Providers · N`: state dot, plugin label, source, npm link; click → select
    + fly.
  - `Consumers · M`: state dot, plugin label, `via` service(s) for the direct
    edge; click → select + fly.
- Each row uses the existing `onSelectNeighbor`-style navigation; the service
  mode is cleared when a plugin is selected; the breadcrumb/history behave as
  they do for node navigation.
- The graph keeps the 0.6 service highlight; the rail is the readable answer.

### Missing services (node mode)

- Under the header: a `Missing services · N` block when the node has unresolved
  injects; each row shows the service name, the declaring state, and a
  `no provider` hint.
- The block is informational: the missing service has no provider node to fly
  to; it explains why the node may be PENDING/FAILED.
- It reuses the existing unresolved badge count; no new table is added.

### Entry and history

- Existing `TopologySearch` service hits open the service inspector. 0.7.0
  additionally lists raw service nodes that the collapsed search misses
  (services with 0 consumers, multiple providers); search hits carry the
  service id/scope; the graph highlight stays by service name.
- The service mode is not a node: selecting a plugin exits it; the breadcrumb
  shows the plugin history; returning to the service is via search (0.7.0) or a
  future “back to service” history entry (0.7.x).

## 5. Findings and suggestions

| Kind | Severity | Suggestion |
| --- | --- | --- |
| `missing-provider` | error (ACTIVE declarer) / warn | Install or boot the provider for `<service>`; verify the inject name. |
| `single-provider-service` | info | Only one plugin provides this service; note it as a bus factor. |
| `critical-service` | warn | Single provider with many consumers; add a fallback or treat it as a deliberate SPOF. |
| `provider-not-active` | warn/error | The service's provider is FAILED/PENDING; consumers may stay unresolved. |

The four facts are surfaced inline: the missing-services block covers
`missing-provider`; the service header's severity badge covers
`single-provider-service` / `critical-service`; the provider rows expose
FAILED/PENDING (`provider-not-active`). The pure `diagnose` returns the generic
`Finding` list for the 0.7.x model/CI export; the rail does not repeat it as a
separate section.

## 6. Non-goals

- Plugin manager install/enable/disable, compatibility/security audit.
- Transitive impact, articulation/dominator SPOF, DAG layers/critical path,
  transitive reduction/cycles, snapshot diff (0.7.x).
- New centrality metrics, community detection/k-core, minimap, state colors,
  focus/ego (0.7.x).
- A service inspector history/back stack beyond the existing node history.
- Model tool / CI export in 0.7.0 (0.7.x; the pure `diagnose` is ready).

## 8. Acceptance

- Service search `tools` → rail service inspector with provider(s), consumers,
  bus factor, critical/single-provider status; click a consumer → that plugin
  is selected/flown to; the service mode clears; `Esc`/search clear exits.
- A node with unresolved injects (fixture) shows the missing service names and
  states, not only a count.
- A service with 1 provider / ≥5 consumers gets `critical-service`; with 1
  provider / 1–4 gets `single-provider-service`; a FAILED provider gets
  `provider-not-active`.
- The 0.6 node inspector behavior, locale parity, token audit and
  `pnpm check` stay green; a pt-test smoke records the service inspector and
  missing-services states.
- No L0/L1/boot-rescue code ships under this label.

## 10. Open questions

1. **Critical threshold**: 1 provider + ≥5 consumers (proposed) or any
   single-provider service; configurable? A lone service with 1 consumer is
   normal; the badge should not cry wolf.
2. **Service scope**: inspect per `s:<scope>:<name>` (proposed) or aggregate by
   label? The search hit key and the graph highlight (by name) must agree.
3. **Service mode history**: no back-to-service in 0.7.0 (proposed), or add a
   lightweight service entry to the history?
4. **Model/CI in 0.7.0 vs 0.7.x**: the pure `diagnose` is in 0.7.0; the model
   tool/CI export are proposed for 0.7.x. Is the UI-only 0.7.0 acceptable?
5. **Findings in 0.7.0**: only the four in §5, or also cycles/duplicate
   provider/orphan/isolated now? (Proposed: four now; the rest with the 0.7.x
   graph work.)
6. **DSH target**: **decided: `0.2.1-rc.2`** — the installed app is
   0.2.1-rc.2; npm `latest` is still 0.2.0-rc.2, so the 0.6.0 row stays
   0.2.0-rc.2 and the 0.7.0 row records 0.2.1-rc.2. The peer ranges moved to
   `^0.2.1-rc.2` with this branch.
7. **navigation-ux 0.7.0 row**: replace B focus/state/minimap with this slice
   and move those to 0.7.x (proposed).
8. **Timeline placement**: rail (current) vs a wider strip under the canvas.
   The rail keeps it next to the selected node; a canvas-bottom variant can
   follow in 0.7.x if the 360px width feels cramped.
